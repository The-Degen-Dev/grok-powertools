R2 Dedupe Reliability Implementation Notes

Created 2026-05-21 for the full reliability implementation pass. This file records implementation decisions, deviations, tradeoffs, and open questions for the R2 dedupe and proof-chain work.

Design Decisions

  • Job-specific notes: This run uses a separate implementation notes file at docs/audits/2026-05-21-r2-dedupe-reliability-implementation/implementation-notes-r2-dedupe-reliability.html so R2 dedupe execution decisions do not get mixed into the earlier full-system audit notes.
  • Subagent split: Exploration is split by ownership area: extension/cloud queue, Cloudflare Worker, and web operations console. Integration decisions remain in the main rollout so cross-boundary behavior stays coherent.
  • Cloudflare authority: The user confirmed the Greymaker Cloudflare account currently logged into Chrome is authoritative for grok-gallery-001. The exact login email is intentionally not copied into this durable artifact. Wrangler OAuth was switched to that account, and the configured account ID, R2 bucket, D1 database, and Worker deploy target now align.
  • No destructive R2 action: Existing R2 media is treated as preserve-only during this pass. The implementation may add verification and reporting, but object deletion, bulk migration, or destructive normalization requires a separate explicit approval.
  • Canonical upload helpers: Cloud upload code now keeps the legacy date-folder helper for local/Vault compatibility but routes R2 upload candidates through canonical media/by-asset/{assetId}.{ext} keys.
  • Verify-before-upload: All media upload paths are being consolidated through a shared helper that hashes the blob, verifies the canonical R2 key, skips matching existing objects, and writes conflicts under a separate conflict path if a canonical key already exists with different evidence.
  • Presign scope: The Worker now only presigns the system upload-test object plus canonical media keys under media/by-asset/ or media/conflicts/. This intentionally blocks stale clients from writing new legacy date-folder media objects.
  • Signed metadata headers: Presign responses now return the exact x-amz-meta-* headers that were included in the signed request, and the extension sends those headers on media, prompt-sidecar, and upload-test PUTs. This keeps sha/content identity metadata attached to R2 objects instead of only appearing in the presign body.
  • Unhoisted metadata signing: The Worker marks signed metadata headers as unhoistableHeaders when generating R2 presigned URLs. Live testing caught that returning metadata headers without this option produces SignatureDoesNotMatch on browser PUTs.
  • Grok asset identity: For assets.grok.com/users/{userUuid}/generated/{mediaUuid}/... URLs, asset identity now uses the last UUID in the URL path. This avoids treating every generated item from the same user UUID as the same media asset.
  • Direct upload success states: Content-script backup handling now treats uploaded, already_present, and conflict_uploaded as successful cloud outcomes, not just queue acceptance. This prevents successful direct R2 writes from being counted as failures.
  • Latest metadata index: The metadata snapshot index now updates by object_key as well as by user_id + kind + content_hash, so a latest metadata pointer can move to a new hash without leaving stale uniqueness conflicts behind.
  • Metadata hash policy: Worker metadata snapshots now hash canonical schemaVersion + data content rather than enqueue timestamps, so unchanged prompt/history/backfill data can be skipped instead of rewritten daily.
  • Local auth fallback: The web app now supplies a non-production Auth.js secret fallback and omits Google provider setup when local Google OAuth env vars are absent, so /api/auth/session returns an unauthenticated null session instead of a 500.
  • Ops console scope: The first web operations console pass uses Worker health/config status plus redacted diagnostic import data. It does not try to scan the local Vault directly from the browser.

Deviations

  • Worker-mediated upload not adopted yet: The current implementation keeps the existing presigned direct-to-R2 PUT path and adds Worker verify before and after upload. A fully atomic Worker-mediated upload would be stronger for multi-writer races, but it would be a larger architectural change and is not required for the single-operator extension path.
  • Schema file replay: Applying the complete schema file to remote D1 failed because the original tables already existed. The dedupe implementation then applied only the new r2_dedupe_index, metadata_snapshot_index, and unique index with IF NOT EXISTS.
  • Live Chrome source mismatch: Chrome was loading the unpacked extension from the canonical skunkworks checkout, not this Codex worktree. For live proof, the loaded checkout is switched to a local mirror branch with the same implementation state rather than reading or copying the saved API key.

Tradeoffs

  • Forward dedupe before migration: The default path is to stop new duplicate writes first, then produce inventory evidence for the existing 30GB. This avoids rewriting or deleting unknown historical objects before canonical identity matching is proven.
  • Canonical blobs plus manifests: R2 date/Saved organization should be represented through manifests or pointer records instead of duplicate media blobs. This keeps browsing and audit views while preventing daily re-uploads of the same old Saved media.
  • Presigned PUT plus verification: Keeping presigned PUT preserves the current browser-to-R2 upload architecture and avoids pushing large videos through the Worker. The tradeoff is that dedupe is deterministic and verified, but not a database-locked atomic write.
  • Ops import before native scanning: A redacted JSON import path gives operators immediate reconciliation visibility without a native companion process. The tradeoff is that automatic Vault scanning remains outside the web app until a trusted local bridge exists.
  • Restrictive presign compatibility: Rejecting noncanonical media keys may break stale extension builds sooner, but it protects the bucket from continuing to accumulate duplicate date-folder objects. The popup test object remains allowed as the compatibility health path.

Open Questions

  • R2 retention window: The current default is last 30 changed manifests or 90 days, whichever keeps fewer versioned metadata objects. Confirm only if a longer compliance/audit history is needed.
  • Existing R2 migration: The current default is report-only for existing duplicate objects. A migration/delete pass should be separately approved after the inventory and canonical match report are available.
  • Atomic media reservation: Current dedupe is verify-before-upload plus conflict isolation. A future Worker-mediated reservation endpoint would be stronger for multiple writers, but is a larger change and should be specified separately if multi-operator uploads become real.
