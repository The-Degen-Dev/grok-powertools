Design Decisions

  • The plan remains one audit plan instead of separate R2, D1, local, web, and Grok plans. The audit's value depends on cross-source joins and conflict reporting.
  • Audit helper scripts are scoped to docs/audits/2026-06-26-production-r2-vault-system-audit/scripts/. This keeps audit machinery close to the evidence and avoids changing product code.
  • The plan uses a single audit runner contract with modes for scaffold, preflight, R2, D1, metadata, local, Worker, reconciliation, report, and artifact validation. This reduces command drift across tasks while keeping output artifacts separated.
  • S3-compatible R2 listing and reads are the preferred raw R2 method because current Wrangler object commands do not expose raw listing. Cloudflare R2 read API or a proven raw Worker binding route remain fallback methods.
  • D1 export is planned through wrangler d1 execute --remote --json --command under Node 24 because current command help confirms that surface.
  • The final report has three verdicts: production R2 internal correctness, current Grok Saved completeness, and local system health. A visual Grok sample cannot prove full current Saved completeness.
  • Local parent-folder inventory is filtered to likely Grok/R2 media candidates. The parent contains unrelated repositories and dependency folders, so scanning every media-like file would create noisy false gaps.
  • After a read-only live Grok probe on 2026-06-28, the planning identity rule is: capture grokPostId from /imagine/post/{uuid} as the preferred Grok Saved item identifier when present. Media URL UUIDs remain variant and storage evidence because the same page can expose multiple media UUIDs for thumbnails, variants, user paths, and active media.
  • A follow-up variant probe sampled one /imagine/post/{uuid} with two in-post thumbnail controls. Switching thumbnails changed the displayed media while the route stayed on the same post UUID, so variants under one grokPostId are real behavior for at least that case.
  • Prompt handling is revised after user clarification: full image prompts, full video prompts, and all available Grok metadata should be stored in the existing Vault data plane. Audit and planning artifacts should stay redacted or hash-only by default, but the Vault itself should preserve the raw prompt text.
  • Automatic alternate_duplicate classification now requires exact SHA-256 equality plus at least one identity-link signal, such as the same grokPostId, media UUID, canonical source URL hash, or prompt sidecar link. Same-hash-only groups stay reviewable until source relationship is known.
  • Physical duplicate cleanup is part of the target plan, not an optional side project. It comes after logical clean state, approved R2 canonical snapshot, D1 projection, app-view validation, and repeated clean audits.

Deviations

  • The spec allows Cloudflare R2 objects API, S3-compatible listing, or a proven raw Worker/R2 endpoint. The plan starts with S3-compatible listing because it can list, head, and stream objects through one read-only path.
  • The plan does not add or modify product route code during audit execution. If existing routes are insufficient, the audit records a blocker instead of adding a new production data path.
  • The plan allows dry-run Next scan and plan routes only after code inspection confirms no production writes. It still excludes approve, run, gap-fill run, and reconcile index routes because the audit does not need approval or execution semantics.
  • The plan does not attempt to prove every current Grok Saved item unless a stable export, API, or other authoritative enumeration appears during execution. It keeps Grok visual inspection as sample evidence by default.
  • The live identifier probe opened one visible Saved media tile and returned the tab to /imagine/saved. It did not run generation, selection, sync, backup, repair, download, delete, share, or post actions.
  • The earlier conservative idea of a separate encrypted prompt vault is intentionally dropped for this owner-only phase. Use the existing Vault/R2 metadata path first, and add more access control only if the product grows beyond a personal archive.

Tradeoffs

  • Alternative considered: use the web Vault preview as the main source. Rejected because preview dedupes and normalizes records, which can hide raw R2 duplicates.
  • Alternative considered: rely on D1 content SHA-256 fields for duplicate proof. Rejected for final duplicate proof because object metadata can drift from actual bytes. The plan hashes R2 media bytes read-only.
  • Alternative considered: download a full local copy of production R2. Rejected because the user approved hashing, not creating a second media corpus. The plan streams or downloads only to hash and discards bytes.
  • Alternative considered: scan every file under the parent media root. Rejected because the parent root contains unrelated app source trees and dependencies. The plan inventories GrokVault fully and parent media candidates selectively.
  • Alternative considered: inspect the live Grok tab first. Rejected because the spec makes raw R2 and local inventory the first proof layer, and live Grok should not be driven until raw inventories are complete or blocked.
  • Alternative considered: treat the current internal assetId or the last UUID in a media URL as the logical Saved identity. Rejected for the canonical model because the live page can expose multiple media UUIDs around one Grok post. The canonical model should keep grokPostId, media UUIDs, R2 keys, and hashes as separate evidence fields.
  • Alternative considered: assume adjacent Saved grid tiles with similar visuals are variants of one generation. Rejected because the verified behavior is route-local, not grid-neighbor-based. The enumerator must classify variants from the opened detail route, not from visual proximity in the Saved grid.
  • Alternative considered: store only prompt hashes/redacted excerpts in the canonical index. Rejected because the product requirement is to archive full prompts and metadata. The safer compromise is not a separate vault, but a rule that raw prompt fields stay in Vault/R2 and do not get copied into committed reports, plans, chat summaries, or broad audit exports.
  • Alternative considered: auto-hide all same-SHA media as duplicates. Rejected because byte equality alone does not prove both objects belong to the same logical Saved asset. The accepted rule needs byte equality plus an identity-link signal.
  • Alternative considered: physically clean duplicate R2 bytes as soon as same-hash groups are found. Rejected because physical cleanup must be generated from the approved canonical index and validated D1 projection, not raw hash groups alone.

Open Questions

  • No planning question blocks execution. Execution must still stop if read-only R2/D1 auth cannot be proven, if raw R2 listing is unexpectedly huge or points outside the prefix, or if browser automation cannot prove it controls the visible Grok tab.
  • If production R2 byte hashing is large enough to trigger rate, cost, or local disk risk, the execution worker should stop and ask whether to continue, sample, or split into a separate hashing run.
  • Before implementing a full Grok Saved enumerator, remove or gate logs that print prompt snippets or source URL snippets. The current backup flow has short prompt/source logging, which is acceptable for debugging but not for a raw metadata capture run.
  • The canonical-index staging plan must not stop at the R2 JSON snapshot. Current recommendation: local-only artifact during read-only reconciliation, append-only R2 JSON snapshot after write approval, D1 projection as the app-facing query layer once the schema is stable, product views reading D1, and recurring reconciliation from D1 back to the R2 snapshot and raw R2 inventory.
  • The clean-state decision should be staged: logical clean first, index clean second, storage clean third. Full system clean requires physical duplicate cleanup to succeed or any remaining candidate groups to be explicitly deferred with reasons.
