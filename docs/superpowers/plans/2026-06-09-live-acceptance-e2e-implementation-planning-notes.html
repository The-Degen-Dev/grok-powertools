Design Decisions

  • The implementation plan treats acceptance as one connected project instead of splitting cloud, extension, web, and harness into separate plans. The shared run ID, correlation ID, verdict model, and evidence workbook make these pieces interdependent.
  • The plan creates a separate execution notes file during Task 1 and this separate planning notes file now. Planning notes explain why the plan is shaped the way it is; execution notes will track what changes during implementation.
  • The plan keeps the existing cloud/wrangler.toml format and uses an ignored generated acceptance config instead of converting the repo to JSONC. The spec preferred JSONC for new Worker configs when appropriate, but the repo already uses TOML and avoiding format churn is safer.
  • The plan starts with pure local contracts before cloud or Chrome work: manifest validation, redaction, verdict classification, Worker acceptance helpers, and preflight classifiers. That keeps TDD possible before any live mutation.
  • The plan makes current tool blockers deterministic preflight output: R2 auth code 10000, stale port 3001, CDP not attached to the existing Chrome session, missing agent-browser/plwr, and unverified installed extension identity.
  • The plan updates Cloudflare and AWS SDK package versions because package registry checks showed newer versions on 2026-06-09. This is included as a planned TDD task, not done silently during planning.

Deviations

  • The spec says the Worker should have an arming record and write lease. The plan starts with request-level acceptance guards and an acceptance schema, then leaves full durable arming workflow to the implementation sequence. Reason: the first red/green tasks need a smaller surface that can be tested without a live D1 database.
  • The spec mentions ops import/display as a review surface. The plan keeps ops secondary and does not make it an independent verifier unless later tasks add object and D1 verification APIs. Reason: the spec explicitly says the harness plus direct Worker/R2/D1 verification is source of truth.
  • The spec allows live canary execution after safer lanes pass. The plan's live canary script only arms and blocks by default; actual Chrome driving remains a final reviewed step. Reason: existing Chrome is user state and should not be automated unless every gate is verified and manually armed.
  • The plan does not attempt to solve Cloudflare R2 auth during planning. Reason: R2 list/create/verify currently fails with auth code 10000, so the correct planning behavior is a hard stop gate, not speculative dashboard or credential work.

Tradeoffs

  • Alternative considered: one large live E2E script first. Rejected because it would mix readiness checks, cloud mutation, browser control, and evidence generation before the safety primitives are tested.
  • Alternative considered: add a full Worker test framework. The plan instead uses TypeScript plus Node's built-in test runner for the first acceptance guard tests. This keeps dependencies small and fits the repo's current cloud setup.
  • Alternative considered: commit a checked-in acceptance Wrangler environment. The plan generates an ignored config from verified environment values. This avoids committing guessed account IDs, bucket names, or database IDs.
  • Alternative considered: treat the web ops page as acceptance proof. The plan treats the evidence workbook as proof and the ops page as display. This avoids a false pass if the UI imports stale or incomplete evidence.
  • Alternative considered: immediately use existing Chrome for validation. The plan defers it until after local gates, isolated browser behavior, cloud acceptance identity, and preflight checks pass. This protects the user's active Grok session and production backups.

Open Questions

  • Confirm whether the acceptance Worker should be a separate Worker name or an environment under the current Worker. The plan currently assumes a separate acceptance Worker name for clearer no-production-touch boundaries.
  • Confirm retention policy for acceptance R2/D1 artifacts after evidence is written. The plan records artifacts but does not decide automatic deletion.
  • Confirm whether final existing-Chrome lane should be manually armed every time. The plan currently requires manual arming for every live run.
  • Cloudflare R2 auth still needs to be fixed before live cloud acceptance can run. The plan blocks on this rather than working around it.
